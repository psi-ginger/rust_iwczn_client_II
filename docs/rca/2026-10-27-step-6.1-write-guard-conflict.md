## Summary

The Step 6.1 implementation reached a partial state and then stopped. The workspace write
guard refuses **every** write to `src/client/driver.rs`, pointing at line 164, which is a
plain struct field declaration (`String` type annotation, no literal value on the line). The
file is therefore frozen in a non-compiling state, and the work cannot be finished in this
workspace until the policy question below is answered.

## Root cause

The guard's credential detector scans written content for a field name drawn from its
credential vocabulary followed by a value. A **type annotation** satisfies that shape:
`name: Type` looks like `name: value`. The first creation of the file was accepted; every
subsequent write is refused, so the detector runs against existing content rather than only
against the changed span.

This is a tooling constraint, not a protocol or logic defect. Nothing in the Step 6.1 design
is disputed by it.

## Evidence

1. `write` (file creation) — accepted.
2. `edit` (two-line change inside one function) — refused: `artifact_secret_detected`,
   `driver.rs:164`.
3. `apply_patch` (same change, unified diff) — refused identically.
4. User adjudicated the hit as a false positive and authorised the change; the retry was
   refused again.
5. User then directed a halt and this escalation. **No bypass was attempted** — no alternate
   write path, no file move, no rename, no removal of the field.

## The exact defect in the frozen file

`DriverConfig::from_env` currently calls:

```rust
Self::from_lookup(std::env::var_os).await
```

`std::env::var_os` has type `fn(&OsStr) -> Option<OsString>` and does not satisfy the
`Fn(&str) -> Option<String>` bound. The required replacement is:

```rust
let lookup = |name: &str| std::env::var(name).ok();
Self::from_lookup(lookup).await
```

Nothing else is known to be wrong; nothing else is known to be right either, since the file
has never been compiled.

## Required decision

1. **Confirm the intent of the rule.** Is the detector meant to match field declarations as
   well as literal assignments? If it is not, this is a false positive that must be worked
   around at the policy level, not in the source.
2. **Pick one resolution and record it here:**
   - **(a) Policy adjusted** — the guard permits type annotations, or a workspace exception is
     recorded. The Implementer resumes from the frozen file, applies the two-line fix, runs
     the five gates and files the delivery note.
   - **(b) Field renamed** — the field name leaves the guard's vocabulary (for example
     `account_token`). This changes the frozen API in `docs/agents/WO-6.1.md` §4, so the
     **work order is amended first** (Scribe lane) and the Verifier checks against the
     amended specification.
   - **(c) Credentials encapsulated** — the two account values move into a dedicated type
     with accessors. Same amendment requirement as (b).
3. Until (1) is answered: do not write `PASSED`, do not edit `TASK_MATRIX.md`, do not commit
   `src/client/driver.rs` as-is.

## Why this is not a code-review item

The Verifier's question here is not "is the driver correct" (it has never compiled) but
"can the frozen API coexist with the workspace write policy". The task is reproducible from
the working tree at `C:\Data\06_Client_Goonzu\rust_iwczn_client_II` with no server, no
network and no credentials.

## Prevention

- Prefer field names outside the guard's vocabulary for non-secret values, or keep secrets in
  a dedicated type whose field name is unambiguous (`account_token`, `key_material`).
- Treat a guard refusal as a scope stop: record it, escalate it, never rename or restructure
  silently to get past it — a silent rename would have hidden a policy decision inside a
  diff.
