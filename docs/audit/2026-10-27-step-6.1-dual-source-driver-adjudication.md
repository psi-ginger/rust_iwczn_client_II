## 0. Why there are two

`docs/agents/` and the multi-agent model do not exist on `main`. Two independent actors
implemented Step 6.1 from the same `CONTRIBUTING_PHASE2.md` scope note — this branch from
WO-6.1 (which freezes the API that Step 6.2 consumes), `main`'s implementer from scope only,
straight to trunk, never having seen §4. Both landed within hours of each other:
`git merge-tree` reports add/add conflicts on `src/client/driver.rs` and
`src/client/driver/tests.rs`, and a content conflict on `src/client/mod.rs`.

## 1. Findings — `origin/main`'s driver (`src/client/driver.rs`, 912 lines)

### 1.1 §4 frozen API (the API Step 6.2 consumes)

| # | Finding | Evidence |
| :--- | :--- | :--- |
| **M1** | Wrong signature and wrong return type: `run(cfg: &DriverConfig) -> Result<SessionReport, DriverError>` — no `&Shutdown` parameter, so a caller cannot inject shutdown, and no `DriverOutcome`. Required: `run(cfg: &DriverConfig, shutdown: &Shutdown) -> Result<DriverOutcome, DriverError>`. The shutdown is built *inside* the in-world leg (`Shutdown::new()`), so nothing outside the driver can observe or trigger it. | WO §4:89–90; `driver.rs:475`, report struct `driver.rs:427`, internal `Shutdown::new()` `driver.rs:710` |
| **M2** | Wrong stage enumeration: `enum Phase` has **10** variants and no `TornDown`; §4 requires a 13-variant `Stage` with `TornDown` on success. A successful session cannot be reported as a stage at all. | WO §4:77–79, §4:82; `driver.rs:160`, variants `driver.rs:162`–`180` |
| **M3** | `DriverError` does not carry the stage reached: 9 of its 17 variants are `#[error(transparent)]` passthroughs with no stage field (`Front`, `WorldList`, `Login`, `Game`, `GameLogin`, `CharInfo`, `WorldEntry`, `Dispatch`, `Teardown`), and 3 more (`SlotEmpty`, `WorldNotFound`, `WorldAddress`, `NotInWorld`) also carry none — only 5 carry `phase`. With `DriverError::Game(#[from] GameError)` a caller cannot tell "died at game login" from "died in world", which is the whole point of §4's requirement. | WO §4:93–95; `driver.rs:187`–`212`, `driver.rs:253`–`284` |
| **M4** | `DriverConfig` has **11** fields, not the frozen 8: it adds `world_id` (`:351`), `heartbeat_interval` (`:361`), `step_timeout` (`:363`) and renames `front`→`front_addr` (`:339`), `game`→`game_addr` (`:342`), `user_id`→`user` (`:344`). §4 states that changing this signature requires a Scribe amendment *and* notice to the 6.2 lane; neither exists. | WO §4:66–75, §4:94–95; `driver.rs:336`–`366` |

## 3. Disposition: what is kept, what is discarded, what is salvaged

**Retained as the source of truth — `src/client/driver.rs` + `src/client/driver/tests.rs` (this branch).**
Rationale: it is the only side that conforms to the frozen API (§4: 13 `Stage` variants, exactly
the 8 `DriverConfig` fields, `run(cfg, shutdown) -> Result<DriverOutcome, DriverError>`,
`DriverError::Stage { stage, source }` carrying the stage on *every* wrapped failure), to §5
(all 8 contracted variable names, all required variables enforced, hand-written `Debug` with
`<redacted>` plus a test, no hardcoded address), to §6.2/§6.4 (stage-observability and
credential tests), and to §7. Its two defects (A1, A2) are remediated in this delivery.

**Discarded — `main`'s `src/client/driver.rs` (912 lines) and `src/client/driver/tests.rs` (138 lines).**
Rationale, per finding: M1–M4 break an API that §4 freezes *for the next lane* — Step 6.2 is
written against `DriverOutcome`, `Stage::TornDown` and the injected `Shutdown`, so keeping
`SessionReport`/`Phase`/internal shutdown would force a rewrite of the consumer instead; M5–M9
mean a deployment built to the documented environment contract does not start; M10 leaves an
open game link and an orphaned watcher on ~30 paths; M11–M12 leave §6.2 and §6.4 untested.
Repairing that in place means changing the signature, the enums, the config shape, the env names
and the teardown structure — i.e. rewriting it back into §4's shape — while the conforming
implementation already exists. `main`'s tests are therefore not carried over either: none of
them exercises `run`, and the two that test non-`driver` behaviour (dispatcher opcodes,
world-address resolution) belong to the modules they test, which are already covered there.

**Salvaged from `main`:**

- `src/main.rs` — the thin-shell shape and the exit-code mapping (0 implicit, 1 runtime, 2
  configuration; `main.rs:8`–`:10`, `:22`, `:41`). Rewritten against *our* API
  (`DriverConfig::from_env` → `Shutdown::new()` → `driver::run(&config, &shutdown)`), which
  closes DoD item 3 that this branch had left open; `DriverError::Config` from inside `run` is
  also mapped to exit 2, per §5.
- `src/lib.rs` — main's two documentation additions (`game::dispatcher`, `client::driver`).
  They describe this tree correctly and merge without conflict.
- `src/client/mod.rs` — the Step 6.1 bullet; this branch's wording is kept (it names the
  governing work order), the difference is documentary only.
- Everything in `1d78ef4` (row-5.1 flake fix: `event_loop/tests.rs`, `game/entry.rs`,
  `net/session.rs`, `TASK_MATRIX.md` row 5.1) — unrelated to Step 6.1, auto-merges.

**Not adjudicated here (deferred to the 6.2 harness):** `main` dispatches the five in-world
opcodes *during* the entry waits, this branch refuses a foreign opcode at the roster gate
(`driver.rs:758`–`763`, a §7-compliant refusal rather than a swallow). Neither the WO's scope
list nor §7 rules this either way, and settling it needs a live conversation — §2 of the WO
assigns that proof to 6.2.
